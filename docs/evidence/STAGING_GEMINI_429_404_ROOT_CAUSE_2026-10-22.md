## Provider calls per learner Run

The browser's `Run` invokes one saved generation then an automatic Judge for that **same attempt** (`automaticJudgeService.ts`, `ProductionApp.tsx`). On a normal aligned task, Judge invokes one Supervisor and five criterion Workers in parallel. No additional LLM synthesis call is made; feedback is assembled deterministically.

| Phase | Logical calls | Provider attempts in current implementation |
| --- | ---: | ---: |
| Generation | 1 | 1; no automatic retry for an uncertain request |
| Judge Supervisor | 1 | 1 normally, at most 2 after a 504 timeout |
| Judge criterion Workers | 5, concurrent | 5 normally, at most 10 after individual 504 timeouts |
| Total aligned Run | 7 | **7 normally, up to 13** (one generation + 12 Judge attempts) |
| Off-task Run | 2 | 2 normally, up to 3; no Workers if Supervisor says no task attempt |

The Judge has a shared 50-second deadline, 12-second first and up-to-24-second recovery windows per stage, capped by the shared deadline. Five Workers can issue provider calls concurrently per learner; 100 simultaneous learners could seek 100 generation calls followed by up to 500 concurrent Worker calls, with up to 1,300 total provider attempts if every aligned stage times out once. This is a ceiling from code, not measured traffic. `productionAiService.ts` additionally has an explicit 429/503 fallback branch, but the saved active configuration has no fallback model, so it does not add attempts there. No SDK-level nested retry was found: `modelRequest` uses direct `fetch`, not a retrying Gen AI SDK.

The saved capacity **harness** has a circuit breaker after a provider 429, which caused the 88 pre-Judge stops. The ordinary signed learner route has no deployment-wide admission queue or circuit breaker; it limits a learner to 40 Judge budget takes per hour (`rebuildRunService.ts`) but that is not a shared provider RPM/TPM limiter. UI snapshot polling every 15 seconds (5 seconds on one view) refreshes data; it does not invoke Gemini. The scheduled roster worker is separate from generation/Judge; SOP ingestion may call a separate Vertex embedding `predict` endpoint. No background generation/Judge scheduler was found in the inspected app call sites.

An uncertain 504 retains the database Judge claim. Subsequent learner retry returns 409 busy until operator reconciliation, preventing duplicate score writes but leaving an ungraded saved output. Definite 429/502 clears the claim when the delete succeeds. The frontend's generic “Retry AI Judge” label does not distinguish these states. A provider 404 is currently mapped to generic application 502 by `productionAiService.ts`, losing the upstream status/message in the learner response; this makes dashboard-to-request diagnosis harder.

## Quota and 404 questions still open

**AI Studio (Gemini Developer API):** the screenshot is insufficient to establish project/key ownership, usage tier, RPM, TPM, RPD, 10-minute spend cap, monthly spend limit, or whether the plotted 404/429 came from an old integration. These are per-project/model/tier values to read from the selected project's AI Studio Rate Limit and Usage/Billing pages; do not substitute published example quotas.

**Current staging (Vertex AI):** the saved configuration points to the global Vertex endpoint and ADC. Google describes standard pay-as-you-go Vertex model throughput as Dynamic Shared Quota, where 429 can indicate temporary shared-pool capacity rather than crossing a fixed RPM/RPD value. The specific billing/quota framework and any project-level controls still need confirmation in Cloud Console. An AI Studio key spend cap does not, by itself, establish a Vertex spend limit. A 404 would require the actual upstream URL, status body, model and timestamp to distinguish an invalid route/model/location/API version from a different AI Studio key client. The saved capacity job had no 404, while 98 generation requests to its same Vertex model returned 200/STOP, arguing against a persistent global route typo during that job, not against an intermittent or separate 404.

3. **P1 — bounded failure handling:** apply jittered backoff respecting provider `Retry-After` for definite 429/503 within a shared budget; avoid nested browser/server/provider retries. Reconcile uncertain claims through a deliberate idempotent operator path; never erase a claim merely because a client timed out, and never fabricate a score.
4. **P1 — observability:** log each provider attempt with phase (`generation`, `supervisor`, criterion key), attempt ordinal, sanitized upstream status/error code, duration, model/endpoint, known tokens, and parent learner request ID. Publish per-minute attempts and 429/404 ratios and queue age; keep prompt/output and secrets out of logs. Keep synthetic harness circuit stops separate from real provider errors.
5. **P2 — capacity/cost choice:** after observing real demand and provider limits, decide whether the current Vertex pay-as-you-go capacity meets the SLO or whether a provider capacity plan is required. Compare actual Vertex billing with AI Studio key usage; no billing/tier/model change is recommended without this reconciliation.
