## Honest 100-request and scheduled-worker gates

Today's user-selected target is **100 logical AI pipelines through an isolated staging load harness**, not 100 Google identities. The proposed job reuses the exact shared generation/Judge implementation and existing runtime identity/Vertex ADC, with no external test endpoint, database credential, actor-quota change or fabricated identity. Accept it only as that named provider/runtime pipeline test. Scheduled-roster operation may use a narrowly OIDC-authenticated internal route on the existing public-transport API when a dedicated private worker is unavailable without IAM changes; the proposed security conditions are below. These are reviewed designs, not yet live pass claims.

1. **Separate targets.** One identity ×100 snapshot calls, 100 synthetic service-side Run pipelines, 100 simultaneous authenticated learner runs, 100 distinct sign-ins, and 100 Run+automatic-Judge pipelines are different tests. Report the actual transport/identity/database/provider path; service load must not be called 100 real users. Never mint fake Firebase identities, bypass app authorization, clear quota/uncertain claims or lower pass requirements to produce a pass.
2. **Reconcile every request.** Save fixed fictional class/lesson scope, unique request IDs, offered/admitted/generated/graded/rejected/uncertain counts, actual model, provider-call attempts, tokens, cost budget, latency p50/p95/p99 and raw errors. A20's 100 offered→40 generated→38 evaluated, with one provider 429 and one timeout, remains a failed capacity target. A 200 health check or average over successes is not recovery proof.
3. **Bound real provider work.** Agree burst/sustained windows and SLO thresholds before acceptance; retain production identity quotas. Generation plus supervisor/five-criterion automatic Judge multiplies provider calls. Admit/queue/reject honestly, cap concurrency and total calls, avoid retrying uncertain outcomes, and verify exact persisted attempts/grades without fabricating results. Do not purchase throughput or change IAM under this task.
4. **Use a recoverable staging release.** Pin source/image/config and capture before/after governance, candidate/active checks and rollback target. Verify pool/Cloud Run/provider bottlenecks with measurements; default pool 5 and earlier max-instance/concurrency values are historical baselines, not automatic tuning recommendations. Keep all Flash, tenant boundaries and score rules unchanged.
5. **Prove scheduled operation end to end.** Validate existing OIDC audience/invoker and private worker route without broad IAM changes, existing Scheduler identity/schedule, due-row claiming, successful per-source reconciliation, replay/no-overlap, failures and source-binding denial. Use only fixed fictional sources and show fresh saved logs/next-sync times plus ordinary authenticated access after add/remove. Do not treat manually calling `runRosterWorker` as Scheduler proof.
6. **Measure backlog freshness.** Current `runRosterWorker` processes at most one connection per invocation to bound the read. A five-minute tick cannot by itself promise every five minutes across 32 due sources. Report claimed/successful/failed/oldest overdue and prove multiple-connection throughput or explicitly state the capacity limit. A worker HTTP200 with zero due work is insufficient.

For the staging API scheduler route, require an explicit server-side staging project/service/enable guard; POST only; verified Google OIDC issuer, exact configured audience and exact existing scheduler service-account email with verified email; and no Firebase/user/header bypass. Caller-supplied class/Sheet/actor/scope must not control the operation. Claim only the two fixed fictional class/source bindings in an atomic bounded transaction before reads or state changes, retaining existing row locks, running-log/generation fences, due-time rules and replay behavior. Do not claim an arbitrary real source and filter afterward. Preserve the legacy dedicated-worker default. Any missing permission to use the existing service account is a blocker to report, not authorization for a new IAM grant. Final review must inspect the actual implementation and real Scheduler principal/delivery logs.

## Corrected live batch: capacity remains blocked

Independent extraction from `apps/promptify-intrepid/outputs/staging-release-2026-10-22-capacity-roster/capacity-revised-logs.json` confirms the normal-budget rerun **failed: 6/100 successful full task evaluations, 30 completed criteria and zero supervisor-only successes**. The run began at `2026-10-21T18:01:30.330Z` (22 October locally), completed all 100 pipeline outcomes in 35.770 seconds, and reported pipeline p95 20.470 seconds across successful and failed outcomes. Generation produced 98 HTTP 200/`STOP` responses and two actual HTTP 429s; no generation 502 occurred in this batch. This difference is consistent with the corrected budget helping generation completeness, but cannot retrospectively prove the missing finish reasons in the first batch or isolate time-varying provider capacity.

Ten Judge pipelines started: six succeeded and four failed. The provider issued **six actual HTTP 429 responses** across phases (two generation, two supervisor, two criterion); the circuit stopped another **88 pipelines before Judge**. Consequently, the error aggregate's 91 Judge/status-429 outcomes means 88 local circuit stops plus three failed Judge aggregates, not 91 provider rate-limit responses. A further Judge aggregate ended with status 504. Telemetry records seven network/timeout attempts, 157 actual provider requests, high-water 100 provider requests, and 66,967 known tokens. Thirteen HTTP calls lacked usage metadata (two generation, three supervisor, eight criterion). Retries and uncertain provider usage remain disclosed; there was no harness-level batch retry and no score or production validation change.

**Staging readiness conclusion:** immediate 100-pipeline shared-engine fan-out is unsupported by the observed provider capacity. Both failed batches remain preserved. This test does not establish 100 authenticated learners, API admission throughput, database persistence capacity, sustained reliability or a latency SLO. No further paid load waves are approved by this review under the present test plan.

The next capacity implementation should use bounded provider admission and a durable queue, with generation/Judge-stage concurrency budgets shared across API instances; enforce queue depth, job expiry and cancellation, preserve identity quotas and uncertain-outcome/idempotency protections, and distinguish queued, running, completed, failed and rejected work honestly in the UI. An in-memory per-instance semaphore alone cannot enforce a deployment-wide provider limit. Choose and observe conservative concurrency before a separately authorized measured trial; use provider 429/backoff signals without blindly replaying uncertain requests. Keep the Flash model and scoring contract intact. Neither a queue nor lower concurrency guarantees that 100 jobs finish within an unstated deadline; an explicit arrival-rate/queue-wait/completion SLO and measured provider quota/latency envelope are required before a capacity claim.
