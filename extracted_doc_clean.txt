Business Requirements Document (BRD) - Prompt Engineering Learning Webapp

1. Executive Summary

Core Problem: Teaching prompt engineering to non-tech (business) users faces challenges due to diverse background domains, demands for personalized/industry-specific coursework, limited instructor resources, and abstract LLM concepts when taught purely through theory without real-time visualization.

Proposed Solution: A lightweight, dedicated web application designed to deliver hands-on prompt engineering training for non-technical users. It allows class managers to upload user rosters via Google Sheets, set user expiration limits, manage class codes, and enable seamless Gmail SSO authentication for students.

Strategic Goals: Democratize LLM and prompt engineering understanding across business functions while maintaining deep conceptual rigor equal to technical training programs.

2. Business Objectives & Value Proposition

Business Objectives:

1. Standardize prompt engineering training across diverse non-technical departments.

2. Reduce instructor setup and operational overhead by automating user onboarding and access control via Google Sheets and Gmail SSO.

3. Accelerate student comprehension of LLM mechanics through interactive, domain-relevant practice environments.

Value Proposition: Provides business users with intuitive, real-time feedback on prompt execution without technical friction, bridging the knowledge gap between tech and non-tech personnel.

6. High-Level Business Rules & Workflows

Business Rules:

• Access Control: Only users listed in the active Google Sheet with non-expired timestamps can authenticate via Gmail SSO.

• Expiration Enforcement: Upon reaching expiration timestamp, user access automatically reverts to read-only or is revoked.

• Class Mapping: Every student record must be linked to a valid Class ID.

High-Level Workflow:

1. Class Manager updates user info and class code on Google Sheet.

2. Webapp synchronizes user roster and sets access expiration rules.

3. Student logs in via Gmail SSO, enters Class ID, and accesses interactive prompt exercises.

4. Student executes prompts in real-time to observe LLM operational principles.

7. Risks, Assumptions, & Dependencies

Risks:

• Google Sheets API rate limits or auth token expiration disrupting login validation.

• LLM API token costs scaling unpredictably during intensive practical classes.

Assumptions:

• Non-tech business users have active Gmail/Google Workspace accounts.

• Instructors maintain structured Google Sheets for active class rosters.

Dependencies:

• Google OAuth 2.0 and Google Sheets API availability.

• Third-party LLM API availability and performance.

Technical Handover Specifications

Google Sheets Sync Logic: Uses Google Sheets API v4 with a Redis token caching layer. The sync worker polls the Sheet every 5 minutes and caches active emails with TTL matching the session expiration.

OAuth 2.0 Auth Flow: Token validation executes via Google OpenID Connect. User email is verified against cached Sheet records before JWT issuing.

LLM API Integration: Requests are proxied through an internal backend service (Node.js/Python) to securely inject API keys (OpenAI / Gemini).

Input Sanitization & Security: All user prompt inputs pass through an input filter to prevent prompt injection and restrict unauthorized API abuse.

1. Executive Summary

As of September 2026, the landscape of prompt engineering has shifted from highly technical syntax manipulation to strategic communication and context management. For business users (non-technical professionals), mastering advanced prompting on Google’s ecosystem—specifically Google AI Studio and Gemini.google.com—unlocks significant productivity gains.

It focuses on leveraging built-in platform features to achieve consistent, high-quality outputs without requiring coding skills. Furthermore, it introduces practical frameworks for observability and monitoring, enabling business users to systematically test, compare, and refine their prompts using A/B testing methodologies and structured evaluation criteria.

2. Key Advanced Prompting Topics (Detailed Breakdown)

2.1. System Instructions & Persona Engineering

Technical Definition & Overview: System Instructions act as a foundational layer of context that dictates the model's behavior, role, tone, and operational boundaries before it processes any user queries.

Practical Use Case: Configuring a "Corporate Communications Assistant" that strictly adheres to the company's brand voice, never uses passive voice, and always formats outputs as ready-to-send emails.

Platform Availability:

Google AI Studio: Native "System Instructions" field in the prompt interface.

Gemini Web Interface: Available via Gems (custom, reusable AI personas).

Best Practices & Implementation Tips:

Use the "Role-Task-Constraint" framework.

Explicitly state what the model should not do (Negative Prompting).

Observability Tip: Test the same query against a base model vs. a model with System Instructions to monitor tone adherence.

2.2. Few-Shot Prompting & Structured Output Enforcement

Technical Definition & Overview: Providing the model with a small set of high-quality examples (input-output pairs) within the prompt to demonstrate the exact desired pattern, format, or logic.

Practical Use Case: Standardizing unstructured data. For example, pasting messy meeting transcripts and forcing the model to output a strict Markdown table containing "Action Item," "Owner," and "Deadline."

Platform Availability:

Google AI Studio: Highly optimized via the "Structured Prompt" interface (allows inserting data tables of examples) and JSON Schema enforcement.

Gemini Web Interface: Achieved manually by typing examples directly into the chat window.

Best Practices & Implementation Tips:

Provide 2 to 3 diverse examples to prevent the model from overfitting to a single edge case.

If using AI Studio, utilize the "Structured Prompt" tab for clean separation of instructions and examples.

2.3. Multimodal Context & Document Analysis

Technical Definition & Overview: Leveraging Gemini's massive context window to process text alongside uploaded files, PDFs, spreadsheets, and images simultaneously.

Practical Use Case: Uploading a 100-page Q3 Financial PDF and a competitor's pricing screenshot, then prompting: "Compare our Q3 revenue growth (from the PDF) against the competitor pricing tiers (from the image). Provide a strategic summary."

Platform Availability:

Google AI Studio: Full support for large file uploads, folders, and Context Caching (which saves costs and time when querying the same large documents repeatedly).

Gemini Web Interface: Native file upload integration, plus Google Workspace Extensions (Drive, Docs, Sheets).

Best Practices & Implementation Tips:

Always ask the model to "cite specific page numbers or sections" when analyzing large documents to reduce hallucinations.

2.4. Chain-of-Thought (CoT) & Step-by-Step Reasoning

Technical Definition & Overview: A technique that forces the AI to articulate its internal reasoning process before delivering the final answer. This drastically reduces logical errors in complex tasks.

Practical Use Case: Evaluating vendor proposals. Instead of asking "Which vendor is better?", prompt the model to: "1. List the pros and cons of each. 2. Weigh them against our $50k budget. 3. Provide a final recommendation based on steps 1 and 2."

Platform Availability: Fully supported on both platforms via prompt phrasing.

Best Practices & Implementation Tips:

Append the phrase "Think step-by-step and show your reasoning before providing the final answer" to complex queries.

4. Lesson Plan Structure: Practicing Advanced Prompting

This lesson plan is designed to help business users master Few-Shot Prompting and Observability.

Module: Standardizing Customer Feedback Analysis

Objective: Learn to transform unstructured text into structured data and measure prompt performance.

Step 1: Generate Sample Data (Prompt for the User)

To practice, you first need raw data. Copy and paste this prompt into Gemini to generate a dataset:

"Generate 5 realistic, messy, and unstructured customer reviews for a fictional software product called 'TaskMaster Pro'. Include a mix of positive and negative sentiments, feature requests, and complaints. Do not format them; make them look like raw internet comments."

Step 2: Baseline Prompting (Zero-Shot)

Ask the model to analyze the data using a basic prompt.

"Analyze these reviews and tell me what customers think."

Expected Output: A generic, conversational summary. Hard to export to a spreadsheet.

Step 3: Advanced Prompting (Few-Shot + CoT + System Instruction)

Apply advanced techniques to the same data.

System Instruction: "You are a strict Data Analyst. You only output data in the exact format requested."

Prompt: "Analyze the customer reviews below. Think step-by-step about the core issue in each review. Then, output a Markdown table with the following columns: [Review ID], [Sentiment], [Core Feature Mentioned], [Actionable Recommendation].

Example 1: Input: 'The app crashes every time I try to export to PDF. Fix it!' Output: | 1 | Negative | PDF Export | Investigate crash logs for PDF export module |

Now process the reviews."

Expected Output: A highly structured, professional table that perfectly matches the provided example.

Step 4: Observability, Monitoring, and Comparison

To ensure business users can monitor AI performance, implement the following observability framework:

The Side-by-Side Test (AI Studio): Open Google AI Studio, use the "Compare" feature. Put the Baseline Prompt in Column A and the Advanced Prompt in Column B. Run them simultaneously.

Evaluation Metrics: Grade the outputs based on 3 business criteria:

Format Adherence: Did it output a table? (Yes/No)

Actionability: Can the output be directly handed to the product team? (Scale 1-5)

Tone: Did it drop conversational filler? (Yes/No)

Tracking: Create a Google Sheet titled "Prompt Library & Performance." Log the Prompt Text, the Task, and the Evaluation Scores. When a prompt consistently scores high, lock it in as a standard operating procedure (SOP) or a Gemini Gem.

·       Vertical slice nhỏ nhất nào đủ để test với người thật nhưng vẫn phản ánh đúng product?

·       Trong các P0 hiện có, feature nào có thể mock ở V0.1 và feature nào bắt buộc phải chạy thật?

·       Có cần Google OAuth + Google Sheet sync thật ngay ở V0.1 hay ưu tiên learning flow trước?

·       Deadline hợp lý cho bản prototype đầu tiên là khi nào và mức “done” mong muốn là demo hay user-testable?

·       Ai sẽ phụ trách phần nào và checkpoint review giữa hai người nên đặt ở đâu?

D. Success Criteria / Testing

·       Prototype cần chứng minh điều gì để được coi là thành công?

·       Nên test với bao nhiêu non-tech users ở vòng đầu?

·       Metric nào quan trọng nhất: completion, time-to-first-prompt, số lần retry, learning gain hay support requests?

·       Sau prototype, decision nào phải có đủ dữ liệu để chốt: UI, API strategy, scoring hay scope production?

7. Kết quả mong muốn sau buổi kickoff

·       Chốt UI direction: Notebook / Playground / Hybrid.

·       Chốt API strategy cần prototype: Managed / BYOK / hỗ trợ cả hai.

·       Chốt vertical slice V0.1 và danh sách feature mock vs feature chạy thật.

·       Chốt owner cho từng phần việc.

·       Chốt deadline/checkpoint cho prototype đầu tiên.

·       Chốt 3–5 success metrics sẽ đo khi test với non-tech users.
